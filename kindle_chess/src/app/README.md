# `src/app` — application lifecycle

The event loop and the chess-session wrapper. This is the layer that owns *time*:
`app.rs` is the only place with a `loop`, and it is the only thread that touches
`Display`.

## File map

| File | Purpose |
|---|---|
| `app.rs` | `impl App` — construction, the main event loop, triple-tap exit, the X11 listener thread |
| `chess.rs` | `impl ChessApp` — typestate transitions and accessors over `ChessBackend` |
| `game.rs` | Two small helpers; `player0_turn` is live, `get_turn_input` is a leftover from the CLI prototype |
| `mod.rs` | `pub mod app; pub mod chess; pub mod game;` |

The *data* for these lives elsewhere: `App` is defined in `models/app.rs`,
`ChessApp`/`ChessBackend` in `models/chess.rs`. This crate consistently splits
struct definitions (`src/models/`) from their impls (`src/app/`, `src/ui/`).

## `app.rs` — the event loop

### Construction

`App::new()` builds the single `Display` (X11 connection + `Renderer` + the mpsc
channel ends + tap-tracking state) and pushes a `HomeScreen` as the only entry on
`screen_stack: Vec<Box<dyn Screen>>`.

### `run()`

Ordering matters and is load-bearing:

1. **Spawn the X11 listener first**, before the first draw, so the `MapNotify`/`Expose`
   events generated by `Renderer::new()` are not missed. (This mirrors the ordering that
   was known to work on-device at `d9fd7cf`.)
2. Render the top of the stack once.
3. Enter the loop, `recv_timeout(16ms)` on the event channel.

### The bootstrap redraw window

The Kindle's e-ink Xorg sometimes drops the very first paint. For up to **1.5 s**, and
only until the first X11-originated event proves the server is alive, the loop re-renders
every **100 ms**. After that it redraws *only* on `Transition::Redraw`.

This is not an optimisation detail to be casually removed: an unconditional 10 Hz redraw
stacks `clear()` + many `put_image()` calls per frame, x11rb auto-flushes them in pieces,
and the result on e-ink is visible flicker.

### Routing

```
X11 thread ──▶ mpsc ──▶ main loop ──▶ screen_stack.last_mut().handle_event(...)
                              │                       │
                        triple-tap check          Transition
```

Every event goes to the **top screen only**. A screen returns a `Transition`
(`models/ui.rs`) which the loop applies:

| Transition | Effect |
|---|---|
| `Stay` | nothing — notably, *no repaint*, which is how e-ink flashes are avoided on dead taps |
| `Redraw` | re-render the top screen |
| `Push(screen)` | push and render the new screen |
| `Pop` | pop, call `on_reveal()` on the revealed screen, then render it |
| `Quit` | break the loop |

`on_reveal()` exists because a pushed screen paints over the framebuffer. Widgets that do
partial/diff rendering (the board, both sidebars) must be invalidated when they come back
into view, or they will diff against a framebuffer state that no longer exists.

### Triple-tap emergency exit

Global, checked before the event reaches any screen: three `TouchKind::Down` events within
**50 px** and **500 ms** of each other quit the app. Taps outside that radius reset the
counter. State lives on `Display` (`tap_times`, `last_tap_pos`) because the gesture works
on every screen.

### The X11 listener thread

A plain `std::thread` blocking on `conn.wait_for_event()`, translating into `AppEvent`:

| X11 event | `AppEvent` |
|---|---|
| `Expose` | `Expose` |
| `ButtonPress` | `Touch { kind: Down }` |
| `ButtonRelease` | `Touch { kind: Up }` |
| `UnmapNotify` | `WindowUnmapped` |
| everything else | dropped |

`KeyPress` → `Quit` is commented out (hardware-button exit).

## Async work from a sync loop

`handle_event` is synchronous, but it runs inside `#[tokio::main]`. The pattern used
everywhere is:

1. A screen spawns work with `tokio::spawn`, handing it a clone of `display.event_tx`.
2. It returns a `Transition` **immediately** — the loop never blocks.
3. The task posts results back as `AppEvent`s, which arrive at whatever screen is on top
   when they land.

That last point is the subtle one: results are delivered to the *current* top screen, not
to the screen that started the work. The auth flow leans on this deliberately —
`ChessAuthScreen` re-emits `ChessReady` and then pops, so the event is picked up by
`HomeScreen` on the next iteration.

The `kick_*` free functions in `src/ui/screens.rs` (`kick_auth_bootstrap`,
`kick_game_stream`, `kick_fetch`, `kick_update_check`, `kick_update_apply`,
`kick_home_puzzle`, `kick_next_puzzle`) are all instances of this pattern.

## `chess.rs` — `ChessApp`

A thin wrapper over `ChessBackend`, which is the runtime side of the typestate:

```rust
enum ChessBackend {
    Offline(BoardLocal),          // stub, see src/local/
    OnlineIdle(BoardAPI<Idle>),   // authed, no game scoped
    OnlineInGame(BoardAPI<InGame>) // a specific game scoped
}
```

- `new_online(token, user)` / `new_offline()` — constructors.
- `attach_game(game_id, my_turn)` — consumes `OnlineIdle` and produces `OnlineInGame`.
  Logs a warning and no-ops on any other backend.
- `online_idle_api()` / `online_in_game_api()` — hand out **clones** for spawned tasks.
  Mutations inside a task stay in the task; propagate via `AppEvent`.
- `token()` — the OAuth token if any. Used by `PuzzleScreen` to make authenticated
  `/puzzle/next` requests; an offline backend returns `None` and puzzles fall back to
  anonymous fetches.
- `apply_game_full` / `apply_turn` — write stream results into the screen's own copy.

Which screens carry which backend:

| Screen | Backend |
|---|---|
| `HomeScreen`, `OngoingChessGamesScreen` | `OnlineIdle` |
| `ChessGameScreen`, `GameActionsScreen` | `OnlineInGame` (via `attach_game`) |
| `PuzzleScreen` | none — only the token |

> The home screen's **Demo** button pushes a `ChessGameScreen` built from the *idle* app,
> so `kick_game_stream` finds no in-game backend and logs
> `"ChessGameScreen has no in-game backend — skipping stream"`. That screen renders an
> empty board and is effectively a layout preview.

## `game.rs`

- `player0_turn(moves, player0_white)` — whose turn it is, from move-list parity. Used by
  `board.rs` on every stream event. Still `println!`s.
- `get_turn_input()` — reads a move from stdin. Dead on the Kindle; a leftover from the
  pre-UI CLI prototype.
